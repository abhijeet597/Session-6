# Migrate Habit Tracker Frontend to React Cleanly

The habit-tracker frontend can be migrated from vanilla JS to React without touching a single Express API route. The winning strategy is **build-alongside then cut-over**: scaffold a Vite + React project in a new `client/` directory, run it against the live backend via a dev-server proxy during development, and only replace the `public/` output files once the React SPA is fully working. The resulting architecture separates concerns cleanly — plain async API functions in `src/api/`, a `useReducer`-backed custom hook for habits state, an `AuthContext` that mirrors the existing localStorage token, and React Router v6 `ProtectedRoute` replacing the current `if (getToken())` guard in `main.js`. The entire migration can be done in seven sequential steps, none of which break the running backend.

## A `client/` directory with Vite keeps the structure clean

The React source lives at `client/` alongside the existing `backend/` directory, scaffolded with `npm create vite@latest client -- --template react` ([Vite Getting Started](https://vite.dev/guide/)). Vite's `server.proxy` option in `client/vite.config.js` forwards all `/api/*` requests to `http://localhost:3001` during development, eliminating CORS friction without any backend changes ([Vite Server Options](https://vite.dev/config/server-options.html)). The minimal proxy entry is a one-liner: `'/api': 'http://localhost:3001'` — no `changeOrigin` or `rewrite` needed because the path prefix is identical on both sides.

For the production build, `build.outDir` is set to `'../dist'` (relative to `client/`) so `vite build` drops hashed assets into a project-root `dist/` directory, and `build.emptyOutDir: true` must be set explicitly because the output path falls outside the Vite project root ([Vite Build Options](https://vite.dev/config/build-options.html)). Express is then updated in two places: `express.static` points to `'../dist'` instead of `'../public'`, and a **SPA catch-all** is appended after all API routes — `app.get('*', (req, res) => res.sendFile(path.join(__dirname, '../dist/index.html')))` — so React Router routes like `/login` and `/signup` return `index.html` on a hard reload rather than a 404. The current project uses Express 4.x (`^4.22.2`), where the bare `'*'` wildcard is valid; an upgrade to Express 5 would require the renamed `'/*splat'` syntax. A root-level `package.json` with `concurrently` wires both processes together: `npm run dev` starts Express and the Vite dev server in parallel, while `npm start` runs Express alone to serve the pre-built `dist/`.

## Eleven components emerge from the existing HTML and JS files

React's "Thinking in React" principle — mirror your data model's structure in your component tree — maps the three existing HTML pages onto a **three-level hierarchy** ([react.dev](https://react.dev/learn/thinking-in-react)). At the root, `App.jsx` wraps `AuthContext.Provider` and `BrowserRouter`. Below it, two public routes (`LoginPage`, `SignupPage`) and one protected route cluster (`HabitsPage` and its children) hang off a single `ProtectedRoute` layout component. Within `HabitsPage`, four leaf components handle distinct responsibilities: `HabitForm` (the add-habit card), `CategoryForm` (the inline category creator, a sibling to `HabitForm` inside the same card wrapper), `Toolbar` (sort and filter controls), and `HabitTable` / `HabitRow` (the rendered list).

**State ownership follows the lowest-common-ancestor rule**: `HabitsPage` holds `habits[]`, `categories[]`, and all filter/sort state because `HabitForm`, `Toolbar`, and `HabitTable` all consume subsets of that data — making `HabitsPage` their nearest shared parent. `HabitRow` holds only its own `isEditing` boolean for the inline edit toggle. The `Toolbar` and `HabitTable` are fully controlled (no own state), receiving their data and callbacks as props. The existing `filter.js` functions (`filterHabits`, `sortHabits`) migrate verbatim as pure utility functions into `src/utils/filterSort.js`; the display list is computed as a derived value on every render (`sortHabits(filterHabits(habits, ...))`), never stored as state, which eliminates the sync bugs that plagued the vanilla `applyFilters` / `renderSorted` pattern. The only required code change in `filter.js` is swapping `module.exports` for ES module named exports so Vite can tree-shake them.

React's synthetic event system makes per-element `onClick` props on each `HabitRow` equivalent in performance to the existing manual event delegation on `#habit-list-body`, because React already attaches all listeners at the document root internally ([Medium: Event Delegation in React](https://medium.com/@john.louis.rumingan/event-capturing-bubbling-and-delegation-in-react-f08b704706a0)). Each of the three row actions (delete, edit, check-in) becomes a callback prop passed down from `HabitsPage` through `HabitTable` to `HabitRow`, replacing the three `addEventListener('click', ...)` blocks in `main.js`.

## A two-layer API design keeps functions testable and hooks reusable

The recommended architecture separates API mechanics from React state in two explicit layers. **Layer one** — plain async functions in `src/api/habits.js`, `src/api/auth.js`, and `src/api/categories.js` — accepts `token` as a parameter and throws on non-OK responses ([Robin Wieruch: React Hooks Fetch Data](https://www.robinwieruch.de/react-hooks-fetch-data/)). These functions have no React dependencies and can be unit-tested directly with Node's built-in test runner, preserving the testing discipline already in `backend/tests/`. **Layer two** — `src/hooks/useHabits.js` and `src/hooks/useCategories.js` — wraps those functions with React state and dispatches to the reducer. Components call only the hook's named action functions; `dispatch` never escapes to the component layer.

The habits state is best managed with `useReducer` rather than six parallel `useState` calls, because sort, filter, loading flag, error flag, and the habit list all update in coordinated sequences ([tkdodo: useState vs useReducer](https://tkdodo.eu/blog/use-state-vs-use-reducer)). The reducer handles actions `SET_HABITS`, `ADD_HABIT`, `DELETE_HABIT`, `UPDATE_HABIT`, `SET_FILTER`, `SET_SORT`, `CLEAR_FILTER`, `SET_LOADING`, and `SET_ERROR`. **Filter values** (category, dateFrom, dateTo) live only in the reducer — they are session-transient and reset on page load, matching current behaviour. **Sort values** live in the reducer too, but are also persisted to localStorage via a `useEffect` that watches `state.sort` and writes `localStorage.setItem(SORT_KEY, JSON.stringify(state.sort))` — the correct React 18 approach, since side effects must not live inside the pure reducer body. The initial sort state is bootstrapped by reading from localStorage on mount, preserving the current UX where sort preference survives page refresh.

The existing `checkInHabit` uses a stale module-level `localHabitsCache` array — a known source of bugs. React replaces this with an **optimistic UI pattern**: immediately dispatch `UPDATE_HABIT` with the projected `completedDates`, fire the API call, then dispatch again with the server's confirmed result on success or roll back to the previous habit object on failure ([freeCodeCamp: How to Use the Optimistic UI Pattern](https://www.freecodecamp.org/news/how-to-use-the-optimistic-ui-pattern-with-the-useoptimistic-hook-in-react/)). This delivers instant feedback without the stale-cache hazard.

## AuthContext and ProtectedRoute replace three separate auth mechanisms

The vanilla app manages auth across three disconnected layers: `getToken` / `setToken` / `clearToken` helpers in `habits.js`, a `window.location.href` guard at the bottom of `main.js`, and full-page navigation between `login.html`, `signup.html`, and `index.html`. React consolidates these into two constructs. `AuthContext` holds a single `token` state value, initialized lazily from `localStorage.getItem('habitTracker.token')` to avoid a flash of unauthenticated UI on first render, and exposes `login(token)` and `logout()` methods that keep context state and localStorage in sync ([dayvster.com: Use Context for Auth](https://dayvster.com/blog/use-context-for-auth/)). No component ever touches localStorage directly — only context methods do. The existing storage key `'habitTracker.token'` is preserved, so users who were already logged in remain logged in after the cutover.

`ProtectedRoute` is a React Router v6 layout component (no `path` prop) that reads `isAuthenticated` from `useAuth()` and either renders `<Outlet />` for authenticated users or redirects to `/login` via `<Navigate to="/login" state={{ from: location }} replace />` ([Dev.to: Implementing Protected Routes 2026](https://dev.to/olumidesamuel_/implementing-protected-routes-and-authentication-in-react-2026-edition-4k6e)). The `replace` prop prevents the login page from appearing in browser history, so the back button does not loop. After a successful login, `LoginPage` reads `location.state?.from?.pathname` via `useLocation()` and navigates there, fixing the current hardcoded `window.location.href = 'index.html'` redirect. The `?signedup=true` query param from the signup flow is replaced by router state — `navigate('/login', { state: { signedup: true } })` from `SignupPage`, read via `location.state?.signedup` in `LoginPage` — keeping the URL clean and ensuring the banner disappears on refresh.

## Seven steps take the app from vanilla to React without downtime

The build-alongside strategy keeps the vanilla app serving real users throughout the migration, with a clean cut-over at the end rather than a risky big-bang switch ([Brainhub: Migrating to React](https://brainhub.eu/library/migrating-to-react)). The sequence is:

**Step 1 — Scaffold tooling.** Run `npm create vite@latest client -- --template react` at the project root. Add the `/api` proxy and `../dist` build output to `client/vite.config.js`. Add a root `package.json` with `concurrently` scripts. Verify `npm run dev` starts both servers.

**Step 2 — Auth skeleton.** Create `src/context/AuthContext.jsx` with `AuthProvider` and `useAuth`. Wire `App.jsx` with `BrowserRouter`, `AuthProvider`, and an empty `Routes` tree containing placeholder `LoginPage`, `SignupPage`, and a `ProtectedRoute`-wrapped `HabitsPage`. The vanilla `public/` files still serve from Express at this stage.

**Step 3 — Migrate LoginPage.** Port `login.html` and the login block from `auth-pages.js` into `LoginPage.jsx`. Connect to `useAuth().login()` and `useNavigate()` for the post-login redirect. Test against the live backend.

**Step 4 — Migrate SignupPage.** Port `signup.html` and the signup block. Replace `?signedup=true` with router state. Test the full signup → login flow.

**Step 5 — Migrate HabitsPage.** This is the largest step. Create `src/api/habits.js` and `src/api/categories.js` (near-verbatim copies of the vanilla `habits.js` functions, with `getToken()` replaced by the `token` parameter). Build `habitsReducer.js`, `useHabits.js`, and `useCategories.js`. Port `index.html` structure to `HabitsPage.jsx`, `HabitForm.jsx`, `CategoryForm.jsx`, `Toolbar.jsx`, `HabitTable.jsx`, and `HabitRow.jsx`. Move `filter.js` to `src/utils/filterSort.js` and convert `module.exports` to named ES module exports.

**Step 6 — Wire the Express SPA fallback.** Run `npm run build` from `client/`. Update `backend/server.js`: change `express.static` from `'../public'` to `'../dist'` and add the `app.get('*', ...)` catch-all after all API routes and the static middleware. Verify hard reloads at `/login` and `/` return the React app.

**Step 7 — Remove the vanilla files.** Delete `public/login.html`, `public/signup.html`, `public/index.html`, and the old `public/js/` files. Add `/dist/` to `.gitignore`. The old `public/` directory can be removed entirely once confirmed clean.

## Conclusion

The migration is mechanically straightforward because the existing codebase already observes the conventions React demands: async/await throughout, `_id` used consistently, auth token isolated under a single key, and filter/sort logic already extracted into a testable pure module. The biggest conceptual shift is replacing imperative DOM manipulation (direct element selection, event delegation, `window.prompt`) with declarative component props and callbacks — a one-for-one translation that the component decomposition table above makes explicit. The two known defects in the vanilla code (`deleteHabit` mutating a stale array, `sortHabits` and `checkInHabit` being undefined) are eliminated automatically by the React architecture: the reducer owns the canonical habit list, optimistic updates replace the stale cache, and undefined function references become compile-time errors in JSX rather than runtime `ReferenceError`s. The migration therefore fixes the four outstanding bugs in CLAUDE.md as a side-effect of the structural change, not as extra work.
